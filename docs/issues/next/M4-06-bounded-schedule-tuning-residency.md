# M4-06 - Bounded schedule tuning and residency-aware dispatch

Problem/result: choose among already-admitted CPU/GPU schedules using bounded cost evidence, data residency, and cache identity. Dispatch must improve end-to-end choices without changing semantics or turning benchmark names into compiler rules.

Dependencies: M4-03, M4-05, M5-01.

Contract and implementation: freeze the M5-01 manifest and baseline versions before tuning; enumerate at most 32 schedules per region, including tile/block shape, vector width, fusion cutoff, frontier chunk, and CPU/GPU threshold, only after typed interaction extraction, physical verification, and numeric-policy checks. A cost record includes logical shape/layout, host/device residency, transfer bytes, launch count, temporary memory, completion, and the three performance timing boundaries. Cache keys include region content, interaction/extraction rule IDs, numeric/layout policy, target capability, toolchain, schedule version, and relevant options. Cache hits revalidate all contracts. Use deterministic bounded tuning with fixed seeds and no runtime tuning; dispatch can choose CPU for small or already-host-resident work and GPU for an admitted profitable plan. Preserve serial/CPU fallback and publication lifetimes. Use M3 naming: hardware-only checks are behind feature `cuda` and test filter `issue_m4_06_gpu`.

Positive cases: forced serial/CPU/GPU controls; tiny host-resident input selects CPU; large device-resident input selects an admitted GPU schedule; transfer-inclusive choice changes when residency changes; bounded candidate enumeration; cache hit/miss and invalidation after source, rule, policy, layout, device, or toolchain changes; generated and library-assisted tracks remain separately labeled. Negative cases: more than 32 variants, tuning on visible production output, stale/forged cache, filename or benchmark-ID matching, unknown cost facts, failed guards, missing device, transfer/launch failure, changed numeric semantics, and partial completion. These must fall back or produce a typed inconclusive result.

Acceptance interface and evidence: add `issue_m4_06_bounded_schedule_tuning`; first require `cargo test --locked -- --list | rg -q 'issue_m4_06_bounded_schedule_tuning'` (a missing match fails), then run `cargo test --locked issue_m4_06_bounded_schedule_tuning`. Record candidate lists, cost inputs, residency transitions, cache keys, selected/fallback plans, and compile/tuning limits. A future authorized GPU run first requires `cargo test --locked --features cuda -- --list | rg -q 'issue_m4_06_gpu'`, then uses `cargo test --locked --features cuda issue_m4_06_gpu -- --ignored --nocapture` and the performance protocol's steady-state, warm host-to-host, and cold-process boundaries; no GPU run occurs now and mock timing is not qualification.

Exclusions/stop: no learned model, unbounded autotuning, multi-device dispatch, semantic relaxation, or CUDA-class claim. Stop when bounded choices are reproducible, cache-safe, and explainable for the frozen performance families.

Shared acceptance: follow `docs/implementation-plan.md`, require a nonzero relevant test selection and run Debug/Release. Explicit GPU qualification must fail on missing hardware; ignored-only or mock-only success does not complete a hardware gate. Source-invalid programs remain errors in every engine; only optimization-specific unknown legality selects a lawful fallback.

## Independent baseline (from M5-01)

The tuning baseline is the faster of forced-CPU and forced-GPU for each program and size, plus the per-family library baselines already in the manifest. The M5-01 held-out hash must be committed before any M4-06 tuning work starts, and tuning uses only the tuning set. Its gate is measured through the M5-01 harness against the frozen `bench/manifest-v1.json` entry for this family and against the M5-01 held-out program set, on the RTX 5070 Ti (sm_120) and the Apple M4 (local Metal); the agent-written same-structure fixture is secondary and never sets the gate.

Amended 2026-10-14: the CUDA performance gates in this contract are measured on an NVIDIA RTX 5070 Ti (sm_120, driver 580.178.04) and, for Metal, on the Apple M4, replacing the earlier RTX A6000 target. No threshold value changes. Every fraction of peak is taken against a reference measured on that same GPU (device-to-device copy bandwidth, or the measured compute peak where this contract defines one), never a datasheet number.
