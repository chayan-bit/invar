# M4-03 - Generated matrix contraction and explicit Tensor Core schedules

Problem/result: recognize a bounded ordinary-loop matrix contraction and generate a tiled NVIDIA schedule without requiring application-authored CUDA. Keep strict ordered FP32 accumulation separate from an explicitly declared reduced-precision/Tensor Core contract.

Dependencies: M4-01, M4-02.

Contract and implementation: require the typed interaction representation and validated extraction before contraction recognition. Match index maps of the form `C[i,j] = combine_k(A[i,k], B[k,j])` with checked extents, layouts, ownership, and a fresh or proven-disjoint output. The strict track preserves the declared dot-product order and rounding policy; it may parallelize independent output cells but may not reassociate the reduction. A separate Tensor Core policy names input formats, accumulator format, conversion/rounding, fused operations, saturation/NaN behavior, and minimum device capability. Introduce any required reduced-precision conversion/operation syntax and its independent source/reference/native meaning in this issue before optimized lowering; IR-only policy flags are insufficient. It must be explicit in source/IR policy and cache identity; enabling a backend flag cannot change strict meaning. Lower to bounded device IR with shared/register tiling, edge masks, physical-access verification, and M3 completion ownership. Generated-track code may use target intrinsics but not a pre-existing whole-operation library; cuBLAS/CUTLASS are separately reported library-assisted references.

Positive cases: zero, one, odd, rectangular, and bounded `256`-class dimensions; independent reference comparison for strict FP32 and each explicitly supported Tensor Core policy; generated source/IR verification on no-device CI; CPU fallback for small or unprofitable shapes; authorized NVIDIA qualification with device-resident and host-to-host timing boundaries. Negative cases: non-affine or data-dependent indices, input/output aliasing, unknown layout, zero-byte overflow, unsupported accumulator or capability, wrong reduction order, implicit TF32/FMA/fast math, partial completion, toolchain mismatch, and a library call mislabeled as generated code. Reject or fall back while preserving the source contract.

Acceptance interface and evidence: add `issue_m4_03_matrix_contraction_tensor_core`; first require `cargo test --locked -- --list | rg -q 'issue_m4_03_matrix_contraction_tensor_core'` (a missing match fails), then run `cargo test --locked issue_m4_03_matrix_contraction_tensor_core`. Cover the performance protocol's `Matrix product` family and report generated and library-assisted tracks separately. Record contraction proof inputs, typed interaction/extraction evidence, policy and layout IDs, tile/launch geometry, generated hash, reference outputs, and fallback decisions. Hardware qualification, when separately authorized, first requires `cargo test --locked --features cuda -- --list | rg -q 'issue_m4_03_gpu'`, then uses `cargo test --locked --features cuda issue_m4_03_gpu -- --ignored --nocapture`; mock compilation and no-device checks cannot satisfy it. No GPU run is performed now.

Exclusions/stop: no sparse/batched contraction, universal GEMM recognition, implicit approximate arithmetic, multi-vendor backend, autotuning, or performance parity claim. Stop when one dense contraction family has strict and explicit-relaxed paths with independent correctness and lifetime evidence.

Shared acceptance: follow `docs/implementation-plan.md`, require a nonzero relevant test selection and run Debug/Release. Explicit GPU qualification must fail on missing hardware; ignored-only or mock-only success does not complete a hardware gate. Source-invalid programs remain errors in every engine; only optimization-specific unknown legality selects a lawful fallback.

## Independent baseline (from M5-01)

CUDA: cuBLAS and CUTLASS (the existing library-assisted track; `CUBLAS_COMPUTE_32F`, f16 inputs for `tc-f16-f32-v1`). Metal: `MPSMatrixMultiplication`. The strict FP32 contract mismatch with cuBLAS SGEMM stays information only, as in the M4 performance gates. Its gate is measured through the M5-01 harness against the frozen `bench/manifest-v1.json` entry for this family and against the M5-01 held-out program set, on the RTX 5070 Ti (sm_120) and the Apple M4 (local Metal); the agent-written same-structure fixture is secondary and never sets the gate.

Amended 2026-10-14: the CUDA performance gates in this contract are measured on an NVIDIA RTX 5070 Ti (sm_120, driver 580.178.04) and, for Metal, on the Apple M4, replacing the earlier RTX A6000 target. No threshold value changes. Every fraction of peak is taken against a reference measured on that same GPU (device-to-device copy bandwidth, or the measured compute peak where this contract defines one), never a datasheet number.
