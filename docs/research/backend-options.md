# First GPU backend research

Status: research decision, 2026-09-22. This document selects a path to falsify; it does not authorize GPU work, add an implementation milestone, or claim performance. M0 remains the nine Rust reference issues. The first device implementation belongs to a later milestone after typed interaction extraction and structured-plan validation exist.

## Recommendation

Use **Rust-generated CUDA C++ source, compiled with NVRTC and loaded through the CUDA Driver API**, as Invar's first device backend. The user continues to write high-level Invar. Rust code owns admission, scheduling, source generation, ABI validation, caching, transfers, launch, completion, and diagnostics. The emitted `.cu` text is a compiler artifact, just as LLVM IR or object code is; it is not handwritten Invar implementation code and is never an application authoring requirement.

This route is the shortest credible test of Invar's central claim for a bounded set of algorithms. It exposes NVIDIA's shared memory, barriers, warp collectives, and matrix instructions without first implementing an LLVM or MLIR target pipeline. Generated source is inspectable and can be compiled with the same NVRTC options as a reviewed CUDA baseline, isolating the quality of Invar's schedule and emission. NVRTC accepts a source string and produces PTX or cubin; the Driver API loads that image and launches a named kernel ([NVRTC 13.4](https://docs.nvidia.com/cuda/nvrtc/), [Driver API](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/driver-api.html), accessed 2026-09-22).

The initial supported family should be small: total, nontrapping, fresh-output `u32` maps and wrapping `u32` reductions/scans extracted from the required typed interaction path. Add `f32` only after its operation-level semantics are frozen. This is a path to CUDA-class performance for algorithms whose structured plan and schedule Invar supports, not evidence that arbitrary sequential programs become fast GPU programs.

## Options compared

| Path | What Rust must own | Strengths | Blocking costs and risks | Decision |
|---|---|---|---|---|
| NVRTC plus Driver API | Plan verifier, deterministic CUDA source emitter, compile/cache wrapper, ABI and launch layer | Smallest path; inspectable artifact; full CUDA feature surface; fair same-compiler comparison with a handwritten baseline | NVIDIA-only; runtime compiler/toolkit dependency; source escaping and CUDA undefined behavior become trust concerns; launch remains an unsafe FFI boundary | **First experiment and first backend** |
| Direct LLVM NVPTX | LLVM IR construction, target setup, address spaces, kernel metadata/calling convention, libdevice linkage, PTX emission | Reuses LLVM concepts from the CPU backend; no generated C++ parser step | Considerably more target detail. NVPTX requires the kernel calling convention, an NVIDIA triple, exact data layout, explicit device address spaces, target intrinsics, and compatible libdevice ([LLVM NVPTX guide](https://llvm.org/docs/NVPTXUsage.html)). Rust `llvm-sys` is tied to LLVM major versions and offers strict versioning ([llvm-sys README](https://docs.rs/crate/llvm-sys/latest/source/README.md)). | Keep as the second backend/control if source emission becomes limiting |
| MLIR through Melior | Dialect construction and verification, bufferization, GPU mapping, lowering/pass pipeline, target serialization, runtime integration | Represents structured loops, memory spaces, and transformations above NVVM; a plausible long-term home for richer scheduling | MLIR's documented GPU pipeline requires already-explicit parallel IR and “doesn't do GPU parallelization” ([GPU dialect](https://mlir.llvm.org/docs/Dialects/GPU/)). Melior wraps the MLIR C API, requires a matching MLIR installation, describes itself and that API as unstable, and records remaining type-safety holes ([Melior](https://github.com/mlir-rs/melior)). This adds a large pinned toolchain before Invar has a stable schedule IR. | Re-evaluate after several source templates expose repeated transformations |
| Generic HVM2-style GPU reducer | Invar-to-net encoding plus Rust-owned concurrent allocator, work queues, atomics, reclamation, demand/failure protocol, and extraction or result materialization | Directly executes local interaction rewrites; useful research comparison for irregular net workloads | HVM2's current repository provides a low-level net IR and C/CUDA generators, says its CUDA modes have higher peak performance but are less stable, and recommends generated C for production ([HVM2](https://github.com/HigherOrderCO/HVM2)). Its graph allocation, atomic linking, and reclamation are a poor first match for regular maps, scans, and tiled GEMM. Copying its C/CUDA runtime into Invar would conflict with the Rust ownership rule; using it unchanged as a third-party runtime would enlarge the trusted base and still require semantic adaptation. | Reference/research backend only, not the first performance backend |

MLIR and HVM2 do not remove the hard problem. Invar must first prove legality and select a structured algorithm. MLIR then lowers explicit parallel operations; a generic reducer executes a different physical algorithm. Neither supplies coalescing, tiling, synchronization, or numerical equivalence merely from the presence of parallelism.

## Device ABI and data layout

Version the device ABI independently of source and cache formats. The first ABI should accept only `extern "C" __global__` functions with flat device pointers followed by fixed-width scalar values and explicit lengths. Use `uint32_t`, `int32_t`, and `uint64_t`; never put Rust `usize`, `bool`, enums, references, slices, or compiler-dependent structs across the boundary. Arrays are contiguous bytes with declared element size/alignment and a checked allocation extent. Shape and stride products are checked on the host before allocation or launch. A kernel manifest records parameter order, width, alignment, mutability, address space, alias facts, grid/block limits, static/dynamic shared bytes, and numeric mode.

The generator must use unsigned arithmetic where Invar requires modulo arithmetic, avoid signed C++ overflow, emit a bounds guard for every partial grid, and assert alignment or non-aliasing only when the verifier proved it. Start with separate input and fresh output allocations. Do not publish or reuse an output until its completion event succeeds.

Generated symbols come only from stable numeric IDs and a fixed mangling scheme. User spelling, source text, file paths, and diagnostics are never interpolated as CUDA tokens. This keeps source generation a typed serialization problem instead of a code-injection boundary.

For comparison, direct NVPTX would require the documented `nvptx64-nvidia-cuda` triple and 64-bit data layout (`e-p:64:64:64-...-n16:32:64` in LLVM's guide), where generic pointers use address space 0 and global objects/pointers need target address-space treatment. The exact complete layout string must come from the pinned LLVM target machine and be asserted in golden IR rather than recopied as an Invar constant. That target-specific burden is a reason to defer it, not permission for the source backend to leave its ABI implicit.

## Toolchain and package boundary

Pin an exact CUDA toolkit/NVRTC version, minimum driver, target GPU model and compute capability, generated-source schema, Driver API binding version, and Rust lockfile in the experiment recipe. Compile for an explicit virtual or real architecture; never accept NVRTC's moving default. A cache key includes all of those fields plus the source hash, flags, ABI version, numeric mode, and schedule parameters. Preserve generated source, compiler log, PTX/cubin, and kernel manifest as evidence. The integrated M3-05 trust policy permits only schedule hints on untrusted persistent cache storage: regenerate source and recompile on cold processes; binary reuse is initially in-process only. Saved artifact hashes do not authenticate executable cache input. CUDA minor-version compatibility has limitations, and NVIDIA states that PTX use can require a driver upgrade ([CUDA compatibility](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html)); therefore a cache hit is valid only after a runtime capability check.

[`cudarc`](https://docs.rs/cudarc/latest/cudarc/) is the leading adapter candidate, not a dependency decision today. Its current documented API connects `nvrtc::compile_ptx()` to `CudaContext::load_module()`, exposes typed device allocations, and marks kernel launch as unsafe. Invar should place that call in one reviewed module whose safe API requires a validated manifest, live buffers, checked extents, and a completion token. If its version-selection/build behavior or safety surface is unsuitable at implementation time, use a minimal generated binding to the same NVRTC/Driver calls instead of adding another abstraction layer.

The alternatives have heavier pins. The inspected `llvm-sys` documentation is 221.0.1 and links by LLVM major; Melior 0.27.x depends on MLIR 22-era bindings. On 2026-09-22, live repository HEADs fetched for research were `cudarc` `5df8c19d0013`, Melior `3e52d3ce0523`, HVM2 `654276018084`, and LLVM `aff1ba103ab3`. These are evidence coordinates, not proposed dependency revisions. This Mac had Rust/Cargo 1.94.0 but no `nvcc` or `nvidia-smi`; no build or device result is claimed.

## Floating-point contracts

Define at least two distinct modes rather than a “strict” Boolean:

1. **Invar strict `f32`** fixes operation order, round-to-nearest-even operations, subnormal handling, signed-zero behavior, explicit fused versus separate multiply/add, and a canonical NaN rule. Compilation uses `--ftz=false --prec-div=true --prec-sqrt=true --fmad=false`; explicit Invar `fma` emits an explicit fused intrinsic. Because CUDA documents that FMA can change results and NaN payload choice is not universally fixed, the kernel must canonicalize NaN results at the points required by Invar's eventual semantics. Parallel floating reductions are ineligible unless the language defines their tree/order or accepts a reproducible bounded-error contract.
2. **Fast `f32`** is an explicit source or execution contract permitting the selected approximations and reassociation. `--use_fast_math` implies flush-to-zero, approximate divide/sqrt, and FMA contraction; it must never be enabled as an invisible optimization. The exact implications and defaults are documented by [NVRTC](https://docs.nvidia.com/cuda/nvrtc/) and NVIDIA's [floating-point guide](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/mathematical-functions.html).

Tensor Core modes form another explicit numeric contract. TF32, FP16, BF16, and mixed-precision accumulation cannot implement strict scalar `f32` by relabeling the operation.

## Synchronization, memory, and matrix roadmap

Make synchronization constructs outputs of verified schedule templates, not arbitrary emitter calls. A block barrier is legal only at a control point reached uniformly by all live threads in the block. Warp shuffle/vote operations carry a proved participant mask; every named non-exited lane reaches the same intrinsic with the same mask. NVIDIA documents invalid behavior or hangs when those conditions fail ([CUDA warp functions](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-extensions.html)). Shared-memory offsets, alignment, bank layout, and total static plus dynamic bytes are computed in the plan and checked against the selected device before launch.

The matrix path should progress through three separately admitted recipes: a correctness-only SIMT kernel, a double-buffered shared-memory tiled kernel, then a vendor or Tensor Core recipe for compatible shapes/layouts/numeric modes. Efficient GEMM uses hierarchical thread-block/warp/instruction tiling, register and shared-memory reuse, and pipelining; [CUTLASS](https://docs.nvidia.com/cutlass/latest/media/docs/cpp/efficient_gemm.html) documents why a naive loop-to-thread mapping is insufficient. For recognized GEMM, a pinned cuBLAS algorithm or CUTLASS recipe provides a useful library-assisted path and independent reference. It does not replace the generated-kernel track required by `docs/performance-acceptance.md`. Invar still owns recognition, legality, layout conversion, algorithm selection, workspace/lifetime handling, and fallback. The manifest reports whether execution used generated SIMT code or a vendor recipe. Tensor Core admission checks element types, accumulation mode, dimensions, strides, alignment, device capability, and the non-strict numeric contract.

## Trust and failure model

The trusted boundary comprises the typed-plan verifier, source emitter, ABI/launch wrapper, NVRTC, driver, device, and any selected vendor library. Generated source is untrusted until compilation succeeds and its manifest matches the launch. NVRTC diagnostics become bounded compiler diagnostics with generated-source coordinates retained for developers; application diagnostics refer to Invar source. Reject unsupported operations or unknown legality instead of silently falling back to approximate device code.

Launch success is not completion. Record immediate Driver API failure and asynchronous event/synchronization failure separately. On compile, allocation, copy, launch, or completion failure, keep the CPU fallback available only when replay is semantically safe. The initial fresh-output, nontrapping fragment permits fallback before publication; a failed device result is discarded. Visible mutation, partial publication, external effects, or uncertain device state prohibit automatic replay. An InFlightUnknown outcome retains all context/buffer/staging resources in the M3-01 bounded quarantine and forbids reuse/replay until confirmed quiescence. Rust drops do not constitute Invar cleanup or prove that in-flight device memory is dead; dropping a pending token transfers ownership to quarantine, not to immediate resource destruction.

## Bounded falsification experiment and gates

After M1 extraction exists and a GPU run is separately authorized, freeze one GPU, driver, CUDA/NVRTC version, clocks/power policy where controllable, and timing protocol. Generate `u32` map, wrapping reduction, and exclusive scan kernels from admitted Invar programs. Compare each with the reference interpreter and with a reviewed handwritten CUDA implementation of the **same algorithm, schedule, launch geometry, and NVRTC flags**. Test lengths `0`, `1`, `block-1`, `block`, `block+1`, a large non-multiple, and the maximum admitted extent. Use canaries and repeated runs; report compile/JIT time, kernel time, transfer-inclusive time, registers, shared bytes, occupancy, and every size rather than only an aggregate.

The backend path is falsified for this first family if any accepted program differs from the reference, a canary changes, a failure publishes output, or the plan validator admits a divergent barrier/invalid shuffle mask/oversized shared allocation. It also fails the performance hypothesis if, after matching schedules and explaining resource differences, generated kernels remain over 1.15 times the median kernel time of the handwritten baseline on both preselected representative large sizes. That ratio is an experiment decision rule, not a release promise. A miss must identify source, PTX/SASS, resource, or launch differences before considering direct NVPTX; changing IR technology without a measured cause is not a remedy.

Required acceptance cases are exact and automatable:

- ABI/map: wrapping `u32` map matches the interpreter at every boundary size; zero length performs no access; invalid extent/alignment is rejected before launch.
- Reduction/scan: exact modulo-2^32 results match the normative algebra, preserving left-to-right order for noncommutative summaries across at least three legal block sizes.
- Float, when admitted: bit-pattern corpus covers signed zero, subnormals, infinities, canonical NaN, contraction-sensitive multiply/add, and explicit FMA in both strict and fast modes.
- Synchronization negatives: mutated plans with a lane-dependent barrier, inconsistent shuffle mask, or excessive scratch are rejected deterministically.
- Failure/lifetime: invalid generated source surfaces the NVRTC log; injected allocation/launch/completion failures leave output unpublished and retain buffers until completion or context teardown.

Only after these gates pass should Invar decide whether source generation is sufficient for the next algorithm family or whether direct NVPTX/MLIR solves a demonstrated limitation.
